# Antigravity Agent Rules

## Git Worktree 규칙

새 프로젝트 시작 시 Git 저장소를 초기화한 후, **반드시 Git Worktree를 생성**해야 한다.

### 적용 조건
- Git 저장소 기반 프로젝트 (`git init` 또는 `git clone` 후)
- 장기 개발 또는 배포가 예정된 프로젝트

### Worktree 생성 기본 패턴
```bash
# 1. main 브랜치에서 첫 커밋 완료 후
git worktree add "../{프로젝트명}-dev" -b develop
```

- **메인 워크트리**: `main` 브랜치 (운영/배포용)
- **추가 워크트리**: `develop` 또는 `feature/*` 브랜치 (개발용)
- 경로는 현재 프로젝트 폴더 **옆에** 생성 (`../프로젝트명-dev`)

### 예외
- 1회성 스크립트 또는 실험용 코드
- Git을 사용하지 않는 단순 파일 편집

## 안티그래비티 핵심 코딩 지침 (Always Apply)

코드를 작성하기 전, 작성하는 동안, 작성한 후에 항상 지켜야 할 **4가지 핵심 원칙**:

### 0. 예스맨(Yes-man) 절대 금지 & 3단계 사전 기술 검토 및 보완 대안 역제안 의무 (Proactive Technical Advisory & Counter-Proposal Rule)
- **무조건적인 동조 및 맹목적 코드 작성 영구 엄격 금지**: 대표님께서 문제 제기를 하시거나 해결 방안, 신규 추가 기능을 요청하셨을 때, "대표님 말씀이 무조건 맞습니다" 식의 무비판적인 동조(예스맨)를 하거나, 부작용 검토 없이 덮어놓고 즉시 코드를 짜서 밀어넣는 행위를 절대 엄격 금지한다.
- **3단계 사전 기술 검토 및 역제안 필수 절차**:
  1. **타당성 및 의도 분석**: 대표님의 문제 제기 및 요구사항의 배경과 타당한 핵심 요지를 명확히 짚어드린다.
  2. **잠재 리스크 및 기술적 부작용 사전 경고**: 제안된 내용을 문자 그대로 바로 코딩했을 때 발생할 수 있는 시스템 충돌(4대 권한 화면 간의 데이터 불일치, Supabase Realtime 백그라운드 동기화와의 레이스 컨디션, 대역폭/트래픽 폭증, 이벤트 중복 발화 등)을 기술적으로 정직하고 소상하게 설명하고 경고한다.
  3. **완성도 높은 보완 대안 역제안**: 시스템의 단일 파이프라인(SSOT)과 안정성을 100% 수호하면서도 대표님의 의도와 목적을 완벽히 달성할 수 있는 보완적인 설계 및 안전한 구현 대안을 먼저 제시하고 상의한 후 작업에 착수한다.

### 0-1. 기존 원칙 상충 시 코딩 즉각 전면 중단 및 선(先)보고 절대 헌법 (Stop Coding & Report First on Principle Conflict)
- **그때그때 맹목적 수정 영구 엄격 금지**: 이미 확립된 기존 원칙이나 `SYSTEM_BLUEPRINT.md` 설계도와 단 1%라도 어긋나거나 상충되는 추가 기능 또는 수정 요청이 발생한 경우, 그때그때 요청에 따라 코드를 임의로 수정하여 불필요한 문제를 연쇄 유발하는 행위를 100% 영구 엄격 금지한다.
- **무조건 작업 즉각 전면 중단 & 선(先)보고 의무**: 기존 원칙/설계도와 충돌하는 순간, 어떠한 예외도 없이 코딩 작업을 즉각 100% 전면 중단한다.
- **보고 필수 내용**:
  1. 기존에 확립되어 있던 정상 원칙/설계도 내용
  2. 이번 요청/수정사항이 기존 원칙과 어떻게 정면으로 충돌하는지
  3. 그대로 수정했을 때 파괴되는 기존 정상 동작 및 시스템 충돌 지점
- **대표님의 명시적 승인 전 착수 영구 금지**: 위 내용을 대표님께 100% 투명하게 먼저 보고드리고, 대표님의 직접적인 최종 판단과 허락을 득한 후에만 다음 단계로 진행한다.

### 1. 먼저 생각하기 & 모호성 즉시 역질문 원칙 (Think Before Coding & Numbered Questions)
- **혼자 넘겨짚기 및 자의적 추측 절대 엄격 금지**: 대표님의 요청이나 질문의 내용, 요지, 증상이 조금이라도 모호하거나 여러 해석이 가능할 때, 혹은 오류/버그 보고를 받았을 때, **절대로 혼자 짐작하거나 임의로 추측하여 성급하게 코드를 수정하지 않는다.**
- **무조건 즉각적인 1~10번 객관식 역질문 의무화**: 질문의 내용이나 요지를 모르면 작업을 즉각 멈추고, **대표님께서 가장 편하게 번호만 선택하실 수 있도록 1번부터 10번까지의 명확한 객관식 세부 질문 리스트로 정리하여 먼저 역질문**한다.
- **실제 사용자 화면 상태 최우선 기준(Ground Truth)**: 가상 테스트 결과에 안주하지 않고, **대표님께서 직접 겪으신 실제 화면 상태(PC/모바일 기기 및 브라우저)를 가장 먼저 절대 기준으로 삼아** 확인 후 작업에 착수한다.
- **섣부른 "100% 완벽 해결" 호언장담 영구 금지**: 대표님께서 직접 검증하고 만족하시기 전까지는 섣부르게 "완벽 해결", "100% 종결" 등의 호언장담을 절대 남발하지 않는다.

### 2. 단순하게 만들기 (Simplicity First)
- 지금 필요한 것만 최소한으로 작성한다. "나중에 필요할지도 모른다"는 이유로 복잡한 확장점/옵션을 추가하지 않는다.

### 3. 수술하듯 고치기 (Surgical Changes)
- 요청받은 버그/기능과 직접 관련된 줄만 최소한으로 수정(diff 최소화)한다. 스타일 변경, 리팩토링, 불필요한 주석 추가를 금지한다.

### 4. 목표를 확인하며 진행하기 (Goal-Driven Execution)
- 작업을 단계별로 나누고, 각 단계마다 구체적인 **확인 방법(테스트/수동 검증)**을 명시한다.
- 단순히 "다 했습니다"가 아니라 "이렇게 확인하면 됩니다"까지 분명히 검증하고 제시한다.

### 5. 땜빵 금지 & 찌꺼기 전수 삭제 후 완전 재구축 원칙 (Clean Slate & Zero Residue Rebuild)
- **무조건 근본 원인부터 규명**: 수정사항이 발생했을 때에는 표면만 덮는 임시 땜빵 패치를 엄격히 금지하며, 전체 흐름에서 근본 원인부터 완벽하게 수정한다.
- **반복 오류 시 찌꺼기 전수 삭제 후 전면 재구축**: 동일하거나 유사한 오류/버그/먹통 현상이 1회라도 반복되는 경우, 덧붙이기식 수정을 즉각 중단하고, 관련된 모든 구형 레거시 코드와 불필요한 찌꺼기(세션 침묵 차단문, 유령 이벤트 리스너, 이중 필터링, 구형 캐시 등)를 **100% 무조건 전수 삭제**한 뒤, 다른 코드에 악영향을 주지 않는 가장 단순하고 무결한 단일 구조로 **처음부터 완전히 새롭게 재구축**하여 영구 종결한다.
- **2차 부작용 원천 방어**: 코드 수정/삭제 시 다른 정상 기능에 일체의 악영향을 주지 않도록 사전 전수 검토 후 적용한다.
- **무조건적 자동 적용**: 사용자가 매번 언급하지 않더라도 모든 작업에 100% 기본 영구 적용한다.

> **한 줄 요약**: 반복되는 오류는 땜빵하지 않고 관련 찌꺼기를 전수 삭제한 후 처음부터 깨끗하게 다시 만든다. 타 코드 영향성을 사전 검증하고 1회에 완벽 종결한다.

### 6. 반복 실패 시 최팀장 선제 재구축 제안 의무 (Proactive Rebuild Proposal Rule)
- **발동 조건**: 동일하거나 유사한 버그/오류가 수정 후에도 **2회 이상 반복**되거나, 땜빵 없이는 해결이 불가능하다고 판단되는 순간.
- **금지 행동**: 그 상황만 모면하기 위한 불필요한 코드 추가, 임시 우회, 덧붙이기식 패치를 **절대 계속하지 않는다.**
- **의무 행동**: 최팀장이 먼저 대표님께 아래와 같이 역제안한다:
  > *"대표님, 이 문제는 반복되고 있어 덧붙이기로는 한계가 있습니다. 5대 에이전트와 협업하여 관련 이중코드·유령코드·찌꺼기를 완전 전수 삭제하고, 설계도 기준으로 처음부터 완전 재구축하는 것을 제안드립니다. 연동된 설계도 영향도를 사전 전수 분석 후 진행하겠습니다."*
- **전제 조건**: 연동·연계된 다른 설계도에 대한 영향도 분석과 해결 방안을 갖춘 상태에서만 재구축을 제안하고 착수한다.
- **무조건적 자동 적용**: 대표님이 매번 언급하지 않아도 최팀장이 스스로 판단하여 100% 영구 적용한다.

## 간판지원단 프로젝트 영구 방어 규칙 (데이터 동기화 & UI 안정성)

앞으로 모든 코드 수정 시 다음 **6대 원칙을 철저히 준수**하여 재발 및 부작용을 원천 차단한다:

### 1. 렌더링 시 세션 데이터 최신화 (Session Sync)
- 영업자/시공사/관리자 화면 렌더링 진입 시, 반드시 최신 `users` / `applications` 저장소로부터 현재 로그인 세션(`activeUser`, `items`)을 100% 동기화한 후 데이터를 표시한다.

### 2. 모바일 폼 상호작용 보호 (Interaction Lock)
- 사용자가 드롭다운(`SELECT`)이나 텍스트입력(`INPUT`, `TEXTAREA`)을 조작/터치 중일 때는 백그라운드 동기화(`SupabaseSync`, `supabase-data-synced`, 타이머)로 인해 화면 전체 DOM이 파괴/재생성(`innerHTML = ''`)되는 것을 절대 금지한다.

### 3. 낙관적 UI 갱신 & 백그라운드 DB 저장 (Non-blocking)
- 상태 변경, 접수 등록 등 사용자 액션 발생 시 로컬 데이터와 화면 UI를 **0초 만에 즉시 갱신하고 알림을 표시**하며, Supabase 클라우드 저장은 비동기 백그라운드로 안전하게 수행하여 대기 지연(딜레이)을 없앤다.

### 4. 이벤트 핸들러 단일 바인딩 (No Duplicate Listeners)
- 드롭다운이나 버튼에 인라인 핸들러(`onchange`, `onclick`)와 자바스크립트 `addEventListener`를 중복으로 등록하여 이벤트가 2회 연속 충돌 발화되는 현상을 방지한다.

### 5. 다각도 정밀 매칭 (Comprehensive Matching)
- 영업자 및 시공사 물건을 분류/매칭할 때는 단일 코드만 비교하지 않고, `bizCode`, `id`, `name`, `items` 등록 ID를 모두 포괄 비교하여 데이터 누락을 원천 방지한다.

### 6. JS 문법 및 구문 자동 검증 의무화 (Zero SyntaxError)
- 스크립트(`app.js`, `dashboard.js` 등)를 수정한 후에는 반드시 `node -c` 구문 검사를 실행하여 문법 오류(중복 `let` 선언 등)가 0건임을 확인한 후 배포한다.

### 7. 최고관리자 대시보드 절대 기준 단일 원천 원칙 (Admin Absolute SSOT Principle)
- **무조건 최고관리자 대시보드가 단일 진실의 원천(SSOT)**이다. "영업자 마이페이지 현황"은 독자 데이터를 갖지 않으며, 오직 "최고관리자 대시보드"의 내용을 100% 그대로 추종한다.
- **부존재 일치 의무 (Non-existence Sync)**: 최고관리자 대시보드에 없는 내용(삭제된 신청서, 영업물건 미승인/해제 건, 삭제된 회원)은 "영업자 마이페이지 현황"에도 **완벽하게 0건(완전 부존재)**이어야 한다. 과거 캐시나 잔재 데이터로 인해 최고관리자 화면에 없는 건이 영업자 화면에 노출되는 것을 영구 금지한다.
- **모든 상태/속성 절대 추종**: 심사 상태, 접수 상태, 진행 상태, 시공사 배정, 현장사진 등 모든 데이터는 최고관리자 대시보드에서 변경되는 즉시 영업자 화면이 실시간으로 100% 동일하게 따라간다.

### 8. 100% 자체 사전 3단계 검증 의무화 (Mandatory 3-Step Self-Verification)
- **무조건 사전 자체 검증 후 보고**: 코드를 수정한 후 사용자에게 보고하기 전, 반드시 백그라운드에서 다음 3단계 자체 사전 검증을 스스로 실행하여 100% 통과했음을 확인한 후에만 결과를 보고한다:
  - **1단계 (DOM 무결성 검사)**: HTML 태그 열림/닫힘 불일치, 누락 태그, 화면을 가리는 투명 오버레이/가림막 존재 여부 자체 전수 검사
  - **2단계 (함수 및 권한 바인딩 검사)**: 호출할 JS 함수가 정상 정의되어 있고, `undefined`, 문법 오류(`node -c`), 또는 잘못된 권한 조건으로 인한 침묵 리턴이 없는지 검사
  - **3단계 (가상 실행 및 데이터 동기화 검사)**: 버튼 클릭 및 액션 발생 시 데이터가 DB/저장소에 정상 기록되고, 대상 화면(영업자/관리자 등)에 정상 리렌더링되는지 가상 시뮬레이션 동작 검증

### 9. 트래픽 폭증 방어 및 대역폭 최적화 영구 규칙 (Bandwidth & Egress Protection Rule)
- **1) 목록 조회 시 사진 데이터 제외 (Column Selection)**: 대시보드 목록(전체 신청서 목록, 영업물건 목록 등)을 동기화하거나 조회할 때는 무거운 Base64 사진 컬럼(`image_url`, `construction_photos`, `construction_invoice`)을 제외하고 텍스트 메타데이터만 선별 조회(`select('id, user_id, owner_name, ...')`)하여 대역폭 전송량을 99% 이상 절감한다.
- **2) 사진 온디맨드 단일 조회 (On-demand Single Fetch)**: 사진 데이터는 사용자가 [사진 보기], [모달 열기], [다운로드] 버튼을 직접 클릭했을 때만 해당 1건에 대해 개별 쿼리(`eq('id', appId)`)로 단일 조회하여 가져온다.
- **3) 사진 강제 자동 압축 (200~300KB Strict Compression)**: 신청서 제출, 현장 사진 업로드, 시공 완료 사진 등록 등 모든 이미지 업로드 시 긴 변 최대 1200px, 퀄리티 0.75, 최대 300KB 이하로 강제 압축(`compressImageFile`, `compressImageToBase64`) 후 DB에 저장한다.
- **4) 불필요한 Polling 타이머 금지**: 모든 실시간 동기화는 Supabase Realtime WebSocket 이벤트 또는 사용자 액션 기반으로 동작하며, 짧은 주기(수 초 단위)의 무제한 전체 DB 재조회 타이머 설정을 엄격히 금지한다.

## [영구 대원칙] 간판지원단 100% '단일 반응형 웹(Single Responsive Web)' 완전 단일화 원칙 (Permanent Single Web SSOT)

- **절대적 단일 원칙**: 간판지원단은 별도의 모바일 앱이 존재하지 않으며, **오직 `index.html` 단 하나의 '단일 반응형 웹(Single Responsive Web)'으로 100% 통폐합(단일화)된 단일 사이트**이다.
- **용어 및 이원화 영구 금지**: "모바일 앱" 등 별개의 앱이나 분리된 PC웹이 존재하는 것처럼 취급하거나 이원화하는 것을 영구 엄격 금지한다. 모든 화면(최고관리자, 영업자, 시공업체, 일반회원)은 단일 반응형 웹 내에서 0초 실시간으로 100% 일원화되어 동작한다.

## 최고관리자 ↔ 영업자 ↔ 시공업체 실시간 3대 권한 동시 연동 필수 매트릭스 (Permanent 3-Way Role Sync Matrix)

신청서 관리 건 & 영업물건 관리 건 모두 다음 **단일 반응형 웹 내 3대 역할 화면이 0초 만에 실시간으로 완벽하게 일치**해야 한다:
1. **`최고관리자 대시보드 (SSOT 단일 기준점)`**
2. **`영업자 전용 현황 대시보드`**
3. **`시공업체 전용 현황 대시보드`**

---

### [업무 그룹 A] 간편 지원 신청서 건
1. **최고관리자 화면**: "신청서 목록"
2. **영업자 화면**: "내 온라인 간편 지원 신청 내역"
3. **시공업체 화면**: 배정된 신청 건 실시간 조회
- **동기화 규칙**: 심사 상태(심사 대기, 서류제출 & 접수예정, 지원사업 탈락, 지원사업 포기), 현장사진 등록, 영업물건으로 변경(`isBizItem`) 토글 시 위 모든 권한 화면에 단일 반응형 웹에서 실시간으로 즉시 100% 동시 반영한다.
- **개발 시 주의사항**: `DataStore.notifyAll()` 또는 `supabase-data-synced` 이벤트 발생 시 렌더링 함수가 빠짐없이 호출되도록 보장해야 한다. 영업자의 신청서 필터링은 `userId`뿐만 아니라 `ownerPhone`, `ownerName`, `referrerCode(bizCode)` 등을 활용한 **다각도 정밀 매칭**을 사용해야 한다.

### [업무 그룹 B] 영업물건 (공단/진흥원 접수) 현황 및 진행상황 건
1. **최고관리자 화면**: "영업물건 진행상황"
2. **영업자 화면**: "내 영업물건 현황 및 진행상황"
3. **시공업체 화면**: "시공업체 진행현황"
- **동기화 규칙**: 접수상태(업체신청, 접수예정, 접수완료), 진행상태(지원대기중, 심사대기, 대상자선정, 간판시공 준비중, 간판시공완료), 시공사 배정 변경 시 `users.items`와 `applications` 양방향으로 즉시 100% 동시 반영한다.
- **SSOT 검증 규칙**: 영업자 및 시공업체 화면의 물건 목록은 최고관리자 대시보드 `applications`에 실존하고 승인/배정된 건만 수집하며, 관리자 대시보드에 존재하지 않는 건은 절대 노출하지 않는다.

## 영업자 매칭 및 신청 식별 3+1 영구 뇌 이식 원칙 (Permanent Salesperson Identification & Assignment SSOT)

영업자 건을 식별하고 담당 영업자 대시보드에 귀속시킬 때는 다음 **3대 신청 경로와 1대 최고관리자 변경 원칙을 100% 준수**한다:

### [3대 신청 경로] (누가 신청하든 영업자코드로 100% 단일 식별)
1. **영업자 본인이 로그인하여 신청한 건**
2. **비회원 점주가 해당 영업자 코드를 입력하여 신청한 건**
3. **이미 가입된 일반 회원(업주)이 해당 영업자 코드를 입력하여 신청한 건**

### [단일 식별 및 매칭 핵심 원리]
1. **영업자 코드(`referrerCode` / `bizCode`) 단일 확인**:
   - 위의 3가지 어떤 경로로 접수되든 데이터에 기록된 **영업자 코드(예: `B-260903`)**는 100% 명확히 확인 가능하다.
2. **신청번호 채번 (`영업자코드 + 순번 3자리`)**:
   - 신청번호 자체가 **`{영업자코드}-001` (예: `B-260903-001`)** 형식으로 생성되므로, **신청번호의 앞자리(영업자코드)**만 확인해도 어느 영업자 건인지 0초 만에 완벽하게 판별된다.
3. **최고관리자 직권 수정/변경 1가지 방법**:
   - 최고관리자가 대시보드에서 신청서의 담당 영업자를 수정/변경하는 경우, 변경된 영업자 코드가 즉시 반영되며 해당 영업자 대시보드(`users.items` 및 신청내역)로 실시간 0초 귀속 연동된다.

## [영구 절대 헌법] 명확한 원칙 및 단일 절대 설계도 보존 법칙 (System Blueprint Preservation Law)

### 1. 단일 절대 설계도 준수 의무
- 프로젝트 루트의 **`SYSTEM_BLUEPRINT.md`**에 명시된 4대 권한(최고관리자, 영업자, 시공사, 일반점주)의 화면 구조, 데이터 흐름, 시안/사진 연동 규칙은 **절대 불변의 시스템 헌법**이다.
- 모든 설계도와 데이터는 100% 일원화되어야 하며, **어떠한 이원화(독자 캐시, 독자 테이블, 독자 모달 분기)도 영구 엄격 금지**한다.

### 2. 착수 전 3선 영향도 분석 의무 (Pre-edit Blast Radius Check)
- 코드를 한 줄이라도 수정하거나 새로운 기능을 추가하기 전, 반드시 다음 3가지를 사전 검토한다:
  1) 이 함수/데이터를 공유하는 다른 권한 화면(예: 점주 vs 영업자)이 있는가?
  2) 이번 수정이 설계도에 정의된 기존 10대 정상 동작 중 단 1개라도 건드리는가?
  3) 최고관리자 SSOT(`applications`)에 위배되는 독자 분기를 생성하는가?

### 3. 자동 검문소(검증망) 통과 의무화 (Mandatory Blueprint Guard)
- 코드를 수정한 후에는 배포 전 반드시 **`npm run verify` (`scripts/verify-blueprint.js`) 자동 검문소를 실행**해야 한다.
- 검문소에서 14개 전수 검사 항목 중 단 1개라도 실패할 경우, 배포(`npm run deploy`)는 원천 차단되며 즉시 원인을 수술식으로 바로잡아야 한다.
- `package.json`의 `predeploy` 훅에 의해 `npm run deploy` 실행 시에도 자동 검문소가 강제 실행된다.
